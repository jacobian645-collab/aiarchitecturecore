Layer 1

Application & experience

Where people meet the system: chat surfaces, copilots inside existing tools, batch jobs, and APIs other services call. This layer owns the contract with the user: what goes in, what comes back, how long they wait, and what happens when the model is wrong.

Components

  • Chat UI, embedded copilots, batch pipelines
  • API gateway, auth, rate limiting, quotas
  • Streaming transport (SSE / WebSocket)
  • Feedback capture (thumbs, edits, escalations)

Design decisions

  • Stream tokens or return a complete answer
  • Synchronous chat vs async job with a callback
  • Human-in-the-loop checkpoints for high-impact actions
  • How citations and confidence are shown

Inside layer 1

The contract with the user: wait, trust and the wrong answer

The model decides what an answer says. Layer 1 decides how long the user waits for it, how far they trust it, and what happens when it is wrong. Those choices shape adoption more than a few points of benchmark accuracy, and none of them live in the weights.

2 · The latency contract: streaming changes which number users feel

Example: 0.5 s to first token, then 400 tokens at 40 tokens/s. Unstreamed, the user feels the total time and crosses the 10-second attention limit. Streamed, they feel only the time to first token, and the text outruns their reading. That is why chat surfaces optimise TTFT. Agents, API callers and structured outputs read the whole response before acting, so for them total latency is still the contract. Past about 10 seconds, switch to an async job with visible progress and a notification.

3 · Design for the wrong answer: autonomy is an interface choice

High impact · easy to undoApprove the planUpdate 400 CRM records. The user approves the plan; a snapshot allows rollback.

Low impact

The same model can sit in all four boxes; what changes is how much the interface lets it do before a person looks. Pair this with the scoped tokens in Identity & policy: the interface asks for approval, the token enforces it.

4 · Every interaction is a label

5 · Design rules

Make stop actually stopCancel generation on the server when the user stops or leaves, or you pay for tokens nobody reads.
Limit by tokens, not requestsOne request can be 50 tokens or 200,000. Quotas and rate limits should count tokens and cost.
Design the "I don't know"An honest abstain screen with a route to a person beats a confident wrong answer.
Show where it came fromCitations let users check an answer in seconds and learn when to trust the system.
Treat every input as untrustedUploaded files, pasted text and web pages can carry prompt injection. Screen them at the edge.
Sandbox UI you did not writeTools can now ship their own interface. Render it isolated and require approval for actions it triggers.

The last rule is new. In January 2026, MCP Apps became the first official MCP extension: a tool can return an interactive interface that hosts such as Claude, ChatGPT, VS Code and Goose render in a sandboxed iframe. AG-UI standardises the event stream between agent back ends and front ends over SSE or WebSockets. Layer 1 is no longer only the screens you build; it is also the screens your tools bring with them.

Layer 2

Orchestration & agents

The control logic between the user and the model. It assembles the prompt, decides whether to retrieve, calls tools, loops until a goal is met, and manages what the model remembers. Most product behaviour lives here rather than in the weights.

Components

  • Prompt templates and system instructions
  • Tool / function calling with JSON schemas
  • Planner–executor loops, routers, sub-agents
  • Short-term (context) and long-term (store) memory
  • Tool protocols such as MCP for connecting systems

Patterns

  • Single call: prompt in, answer out
  • Chain: fixed sequence of calls
  • Router: classify, then send to a specialist model or prompt
  • Agent loop: reason → act (tool) → observe → repeat, with a step budget
Agent cost ≈ steps × (prompt tokens + output tokens) — context grows each step, so cost rises faster than linearly without summarisation or caching.

Inside layer 2 ↓ five patterns, the cost and reliability maths of the loop, and the context budget.

Inside layer 2

Who drives the loop, and what each turn costs

Orchestration is the code between the user and the model: it builds the prompt, calls tools and decides what happens next. Its first design choice is who picks the next step, your code or the model. Everything else in this layer — cost, reliability, how much context the model has to wade through — follows from that answer.

1 · Five patterns, from code-driven to model-driven

PatternWho picks the next stepPredictabilityCalls per taskUse it when
Single callNobody: there is no next stepHighest1Classifying, extracting, or drafting from context you already have
ChainYour code, in a fixed orderHighKnown in advanceThe recipe is stable: outline, draft, check
RouterThe model picks a branch once; code runs itHigh1 decision + 1 specialistMixed traffic where a cheaper model or specialist prompt handles most cases
Orchestrator–workersThe model plans subtasks; workers run them, often in parallelMediumDepends on the planResearch or code changes whose subtasks can't be listed up front
Agent loopThe model, every turn, until it stops or hits a budgetLowestUnknown until it finishesOpen-ended work where the path depends on what the tools return

Anthropic's Building effective agents draws the line between workflows, where code fixes the path, and agents, where the model chooses it. Each row down buys flexibility and gives up predictability and cost control, so move down only when the task needs it. The router row is where a decision model like JEV fits.

2 · An agent re-reads its whole history on every turn

365kinput tokens across 20 turns
=
4.6×20 separate calls (80k)
→
~74ktoken-equivalents with prompt caching

Example: a 4,000-token prefix, and each turn adds about 1,500 tokens of reasoning, tool call and tool result. Because every call re-sends everything before it, total input grows with the square of the number of turns, not in step with it. Prompt caching changes the bill, not the shape: cached reads cost about a tenth of normal input on the major APIs (less on some newer models), so this run costs roughly 80% less. The context is still 32,500 tokens long by turn 20, and the model still has to read all of it. That is panel 4. Output tokens are not counted here.

3 · Reliability compounds too

Each step succeeds5 steps10 steps20 steps
99%95%90%82%
95%77%60%36%
90%59%35%12%

If every step must succeed and failures are independent, the run succeeds at the per-step rate raised to the number of steps. A step that works 95% of the time sounds solid; chain 20 of them and the run finishes cleanly about one time in three. Real agents beat this table because they notice errors and try again — that is what the loop is for. But recovery only happens if it is designed in: tool errors the model can read, steps that are safe to retry, and checks before the steps where a wrong turn gets expensive.

4 · The context window is a budget, not a bucket

In the windowWhy it growsWhat to do
System instructionsIt shouldn't; this is the stable prefixKeep it first and unchanged between turns, so it caches
Tool definitionsEvery connected tool adds its schema to every callLoad only the tools this task needs; search for tools instead of listing hundreds
Retrieved contentWhole files and search results pasted inFetch just in time; keep references (paths, IDs) and pull content when needed
Turn historyEvery turn appends to itCompact: summarise older turns and drop stale tool output
Working notesPlans and progress the model must carry forwardWrite them to a file or memory store and re-read on demand
Sub-agent outputA helper returns its full transcriptHave sub-agents return a condensed result, not their working

Bigger windows raise the ceiling; they don't make filling them free. Chroma tested 18 models in 2025 and found accuracy falls as input grows, even on simple retrieval tasks, a pattern it named context rot. On the LongMemEval benchmark, models did markedly better with a focused prompt of about 300 tokens than with the full history of about 113,000. Anthropic calls the discipline context engineering: give the model the smallest set of high-signal tokens it needs for the next step.

5 · Design rules

Start with the least autonomy that worksA chain you can test beats an agent you can't. Add a loop when the path truly depends on what the tools return.
Give every run a budgetCap steps, tokens, wall-clock time and spend. When a cap is hit, stop and report; don't carry on silently.
Keep the prefix stableCaching matches on the prefix. A timestamp at the top of the system prompt breaks the cache on every call.
Make tool errors readableReturn "customer ID not found; try search_customers", not a stack trace. The model can only recover from what it understands.
Make steps safe to retryPut idempotency keys on writes, so a retried step doesn't send the email twice.
Trace every turnLog prompts, tool calls and results under one trace ID so a bad run can be replayed, and so governance has its evidence.

Layer 3

Knowledge & retrieval

Retrieval-augmented generation (RAG) grounds answers in your own documents without retraining. Quality is decided mostly by chunking and ranking, not by the model.

Ingest path

  • Parse (PDF, HTML, tables) and clean
  • Chunk: typically 200–800 tokens with overlap, or by document structure
  • Embed each chunk into a dense vector
  • Index in a vector store (HNSW, IVF-PQ) with metadata filters

Query path

  • Rewrite or expand the query
  • Hybrid search: dense vectors + BM25 keywords
  • Rerank top-k with a cross-encoder
  • Pack the best passages into the prompt with source IDs
similarity(q, d) = cos θ = (q · d) / (‖q‖ ‖d‖)  ·  measure with recall@k, MRR, and answer faithfulness

Inside layer 3

Most RAG failures happen before the model writes a word

When a RAG system gives a wrong answer, the instinct is to blame the model or rewrite the prompt. More often the model never saw the right passage: it was never indexed, it ranked 31st, or it was cut when the context was packed. Generation can only be as good as what retrieval hands it, so this layer is where answer quality is won or lost.

1 · Seven places a RAG system fails

Failure pointStageWhat it looks likeFirst fix
1 · Missing contentCorpusThe answer isn't in any indexed document, but the system answers anywayCoverage checks; a clear "not in the documents" response
2 · Missed the top-ranked documentsRetrieve & rankThe right chunk exists but ranks below the cut-offHybrid search, query rewriting, a reranker
3 · Not in contextAssembleRetrieved, then dropped when the prompt was packedRerank before trimming; dedupe; budget the context
4 · Not extractedGenerateThe answer is in the context, but noise or contradictions hide itFewer, better passages; flag conflicting sources
5 · Wrong formatGenerateThe model ignores the requested table, list or schemaStructured output with validation
6 · Incorrect specificityGenerateToo general or too detailed for what was askedClarifying questions; examples in the prompt
7 · IncompleteGenerateLeaves out information that was in the contextBreak multi-part questions into sub-queries

From Barnett et al. (2024), drawn from three production RAG case studies in research, education and biomedicine. The first three failures happen before generation, and an end-to-end "was the answer right?" score can't tell them apart from model errors. You only see them if you measure the retriever on its own (panel 5).

2 · Retrieval is a pipeline you can tune, step by step

Anthropic's 2024 Contextual Retrieval experiment, averaged across several domains. Contextual embeddings prepend 50–100 tokens of model-written context to each chunk before embedding it, so a chunk that says "revenue grew 3%" also says which company and which quarter. That one-time step cost about $1.02 per million document tokens with prompt caching. Adding keyword search (BM25) and then a reranker, which takes the top 150 candidates and keeps the best 20, cut missed retrievals by two-thirds without touching the generating model. These are a vendor's own benchmark numbers; the pattern, not the exact figures, is what transfers.

3 · Why hybrid search: meaning and exact matches fail differently

ChunkDense rankBM25 rankRRF scoreFused rank
B · "Error ERR-4012: token expired"311/63 + 1/61 = 0.03231
A · "Troubleshooting sign-in problems"191/61 + 1/69 = 0.03092
C · "Resetting your password"2—1/62 = 0.01613

Query: "what does ERR-4012 mean?" Dense embeddings match meaning, so they rank general sign-in pages highly but blur exact strings like error codes, part numbers and names. BM25 matches the exact token. Reciprocal rank fusion combines the two lists without tuning: each list contributes 1 / (60 + rank), and the sums are re-sorted. The chunk that both methods rate well wins. Here, the exact error page rises to the top.

Start with a golden set of 50–200 real questions, each labelled with the passage that answers it, plus some questions the corpus can't answer. 6 · Design rules

Chunk by structure, not by countSplit on headings, sections and table boundaries. A chunk that cuts a table in half answers nothing.
Hybrid by defaultDense plus keyword search, fused. It costs little and fixes the exact-match blind spot.
Retrieve wide, rerank narrowPull 50–150 candidates cheaply, then let a reranker choose the few that enter the prompt.
Filter permissions before rankingStore access rights with every chunk and filter on them in the query, so restricted text never reaches the prompt.
Design for "not in the documents"When retrieval scores are low, say so and route to a person rather than letting the model fill the gap.
Version the indexChanging the embedding model means re-embedding everything. Record which model built each index, and re-index changed documents promptly.

Layer 4

Foundation model

Almost every current large language model is a decoder-only transformer: a stack of identical blocks that turns a sequence of tokens into a probability distribution over the next token. Variants change the attention pattern, the feed-forward layer, or add encoders for images and audio.

Building blocks

  • Tokenizer (BPE / SentencePiece), vocab ~32k–256k
  • Token embeddings + rotary positions (RoPE)
  • Self-attention: multi-head, grouped-query (GQA)
  • Feed-forward (SwiGLU) or Mixture-of-Experts
  • RMSNorm and residual connections

Variants to know

  • Dense: every parameter used per token
  • MoE: router picks top-k experts; large total, small active params
  • Multimodal: vision/audio encoder projected into token space
  • Long context: RoPE scaling, sliding-window or sparse attention

Inside layer 4 ↓ mixture-of-experts: why a trillion-parameter model can cost less per token than a 405B dense one.

Inside layer 4

One transformer block

Each block reads the running representation (the residual stream), lets every token look back at earlier tokens through attention, then transforms each position independently with the feed-forward layer. Residual connections (dashed) add each sub-layer's output back to its input, which is what lets very deep stacks train.

Attention(Q, K, V) = softmax( Q·Kᵀ / √dk + mask ) · V
  • Attention mixes information across positions; cost grows with sequence length squared in prefill.
  • Feed-forward holds most parameters (about two-thirds in a dense model) and much of the stored knowledge.
  • GQA shares key/value heads across query heads to shrink the KV cache.
  • MoE swaps the single feed-forward for many experts; only top-k run per token.
Inside layer 4

A trillion parameters, 32 billion at work

The block diagram above has a small note on the feed-forward layer: "or MoE experts". That one swap explains how open models grew past a trillion parameters in 2024–25 without getting proportionally more expensive to run. Kimi K2 holds about 1,040 billion parameters, yet each token passes through only 32 billion of them, about 3%. In a mixture-of-experts (MoE) model, "how big is it?" has two answers: total parameters set the memory bill, active parameters set the compute bill.

1 · How a token picks its experts

An MoE layer replaces one large feed-forward network with many smaller ones, the experts. A small learned router scores every expert for each token at each MoE layer, keeps the top k, and mixes their outputs by the router's weights. Attention, embeddings and norms stay shared. The idea is old: Shazeer et al. made it work at scale in 2017, and Google's Switch Transformer (2021) sent each token to one expert and pre-trained up to 7× faster than T5-Base on the same compute. Mixtral 8x7B (Dec 2023) uses 2 of 8 experts and, in Mistral's words, runs "at the same speed and for the same cost as a 12.9B model". Despite the name, experts rarely map to subjects: Mistral's analysis of Mixtral found no clear topic specialisation, with routing following syntax more than domain.

MoE moves the bottleneck from compute to memory capacity and the links between GPUs. In return you get the quality of a much larger dense model: Mistral reported that Mixtral, with 12.9B active parameters, beat Llama 2 70B on most benchmarks.

4 · What MoE costs you

ProblemWhy it happensWhat teams do
Memory capacityEvery expert must sit in GPU memory, even though only a few run per tokenSize the cluster by total parameters; quantise expert weights (gpt-oss ships them at 4 bits)
Load imbalanceThe router learns to favour a few experts; they become hot spots while others starve, or "collapse" and stop learningAdd a balancing loss (Switch); DeepSeek-V3 instead nudges a per-expert bias, avoiding an extra loss term; cap tokens per expert
CommunicationWith experts spread across GPUs, every MoE layer sends tokens out to their experts and back (all-to-all)Keep expert groups inside the fastest interconnect; DeepSeek-V3 limits each token to experts on at most 4 nodes; overlap compute with transfers
Small batchesAt low traffic each expert gets a handful of tokens, so its matrix multiplies are small and GPUs sit idleMoE pays off at high, steady throughput; for quiet self-hosted workloads, a smaller dense model can be cheaper
Training stabilityRouter logits can grow and destabilise training; fine-tuning can shift routing and starve rare expertsRouter z-loss (ST-MoE, 2022); evaluate per domain after fine-tuning; adapt shared layers first

None of these show up in a benchmark table. They show up in the serving bill and the p95 latency, which is why an architecture review should ask for both parameter counts and the batch size behind any throughput claim.

6 · Design rules

Size memory by total, cost by activeTotal parameters decide how many GPUs you need. Active parameters decide compute per token. Plan for both.
Always quote both numbersWrite "37B active / 671B total". Comparing an MoE's total with a dense model's size misleads in both directions.
Benchmark at your batch sizePublished MoE throughput assumes full batches. Measure at your real traffic before you commit hardware.
Keep experts on the fastest linksPlace expert-parallel groups inside one server's interconnect where possible; cross-node all-to-all is where latency hides.
Watch expert load in productionLog each expert's share of tokens. Imbalance shows up as tail latency before it shows up as quality.

Layer 5

Training & adaptation

A model passes through stages, each with different data and objectives. For most enterprise work the choice is not whether to pretrain but which adaptation to apply on top of an existing model.

Stages

  • Pretraining: next-token prediction on trillions of tokens
  • Supervised fine-tuning: instruction–response pairs
  • Preference tuning: RLHF (reward model + PPO) or DPO
  • Distillation: a small model learns from a larger one

Adaptation ladder (cheapest first)

  • Prompting and few-shot examples
  • RAG for knowledge that changes
  • Parameter-efficient tuning: LoRA / QLoRA adapters
  • Full fine-tune for behaviour and format at scale
Training compute ≈ 6 · N · D FLOPs (N params, D tokens)  ·  compute-optimal ≈ 20 tokens per parameter (Chinchilla)

Inside layer 5 ↓ why a 1.3B model beat a 175B one, how LoRA makes adaptation cheap, and the adaptation ladder.

Inside layer 5

A 1.3B model beat a 175B one

In OpenAI's InstructGPT study, people preferred answers from a 1.3-billion-parameter model to answers from the 175-billion-parameter GPT-3, a model with over 100 times more parameters. The architecture was the same. The difference was post-training: a few tens of thousands of prompts of human demonstrations and rankings, on top of a model pre-trained on hundreds of billions of tokens. Pre-training gives a model its knowledge; post-training decides how it uses it. For enterprise teams, the useful corollary is that adapting a model costs a tiny fraction of building one.

Every stage after pre-training uses a sliver of its data, which is why post-training is where most teams, and most of a model's personality, actually live. LIMA (Meta, 2023) pushed this furthest: a 65B model fine-tuned on just 1,000 carefully curated examples gave answers judged equivalent or better than GPT-4's in 43% of cases. The authors' reading: knowledge comes from pre-training, and fine-tuning mostly teaches format.

2 · 100× fewer parameters, and still preferred

From Ouyang et al. (2022). Squares are drawn to scale by area. The method: fine-tune GPT-3 on demonstrations, train a reward model on human rankings, then optimise against it with reinforcement learning. It halved made-up facts on closed-domain tasks such as summarisation. It wasn't free: the paper reports an "alignment tax", small drops on some academic benchmarks, which they reduced by mixing pre-training data back into the RL step. Any adaptation can trade away skills you didn't test, which is why panel 6 starts with evals.

3 · Why adapting is cheap: LoRA

350 GB → 35 MBsaved checkpoint per task
1.2 TB → 350 GBGPU memory to train
~10,000×fewer trainable parameters

Low-rank adaptation (Hu et al., 2021) freezes the original weights and learns a small update, W + B·A, where B and A are thin matrices of rank r. On GPT-3 175B, adapting only the query and value projections at rank 4 matched or beat full fine-tuning on the paper's tasks, trained about 25% faster, and adds no latency at serving time once B·A is merged into W. QLoRA (Dettmers et al., 2023) went further: it fine-tuned a 65B model on a single 48 GB GPU by keeping the frozen weights in 4-bit, and its Guanaco model reached 99.3% of ChatGPT's score on the Vicuna benchmark after 24 hours of training.

Build the eval set firstTask examples plus a regression suite for skills you need to keep. Without it you can't tell gains from the alignment tax.

Layer 6

Inference & serving

Serving splits into two phases with different bottlenecks. Prefill processes the whole prompt in parallel and is compute-bound; it sets time-to-first-token. Decode produces one token at a time, rereads all weights and the KV cache each step, and is memory-bandwidth-bound; it sets time-per-output-token.

Techniques

  • KV cache, with paged allocation (PagedAttention)
  • Continuous (in-flight) batching
  • Quantization: FP8, INT8, INT4 weights
  • Speculative decoding with a draft model
  • Prefix / prompt caching for shared system prompts

Metrics

  • TTFT: time to first token (ms)
  • TPOT: time per output token (ms)
  • Throughput: tokens/s per GPU
  • Goodput: requests/s that meet the latency SLO
  • Cost per 1M input / output tokens
Weights memory = params × bytes  →  70B × 2 B (FP16) = 140 GB; at INT4 ≈ 35 GB
KV cache per token = 2 × layers × kv_heads × head_dim × bytes

Inference compute ≈ 2 · N FLOPs per generated token

Inside layer 6

The KV cache, explained

A language model writes one token at a time. To pick each new token, attention compares it with every earlier token using their keys (what each token offers to be matched on) and values (what it contributes once matched). Those keys and values never change once computed, so serving engines keep them in GPU memory instead of recomputing them. That store is the KV cache. It makes generation fast, and it is usually what limits how many people one GPU can serve.

1 · What the cache saves

To produce token 5, the model needs keys and values for tokens 1 to 5. Without a cache it recomputes all of them at every step. With a cache it computes only the newest one and reads the rest. Over a 1,000-token answer that is 500,500 key/value computations per layer without a cache, against 1,000 with one.

Make each token smaller

  • Offload: move idle conversations to CPU memory or SSD

Inside layer 6

Serving one user, an H100 spends 99.7% of each step waiting on memory

An H100 can do 989 trillion BF16 operations a second and read 3.35 TB from memory a second. Serve an 8B model to one person and each new token needs about 16 billion operations, but also a full read of the model's 16 GB of weights. The maths takes 0.016 ms. The read takes 4.8 ms. So for one user the chip's maths units sit idle for 99.7% of every step. Decode is a memory problem, not a compute problem, and nearly every serving technique is a way to get more tokens out of each trip to memory. The KV cache, explained asked how many conversations fit on a GPU; this section asks how fast they run.

1 · Two jobs, two bottlenecks

Prefill processes thousands of prompt tokens at once, so each byte of weights it reads is used thousands of times and the GPU's maths units stay busy. Decode produces one token per conversation per pass, so the same read is used once. One request goes through both, which is why a single "latency" number hides two different problems.

The H100 can do about 295 operations for every byte it reads (989 TFLOPS ÷ 3.35 TB/s). Decode at batch 1 does about 1: 2 operations per parameter, 2 bytes per parameter. Where you sit on this curve is a product decision: chat needs a TPOT floor, overnight batch jobs only care about the total. Two techniques made large batches practical. Continuous batching (Orca, OSDI 2022) adds and removes requests at every step instead of waiting for a whole batch to finish; on GPT-3 175B it gave 36.9× the throughput of NVIDIA FasterTransformer at the same latency. PagedAttention (vLLM, SOSP 2023) stores the KV cache in small blocks like OS memory pages. Earlier systems reserved space for the longest possible answer, so as little as 20.4% of KV memory held real tokens; vLLM reached 96.3% and 2–4× the throughput at the same latency.

Bandwidth ceilings only: 16 GB of BF16 weights, 128 KiB of KV cache per token, 3.35 TB/s. They ignore attention maths, kernel overheads and imperfect overlap, so real engines land below them. The shape is what transfers.

4 · Speculative decoding: spend the idle maths on guesses

Checking 4 tokens costs the large model about the same as writing 1, because the pass is paid for in memory reads (panel 2), not maths. A small draft model guesses ahead; the large model verifies all the guesses at once and keeps the longest correct run, plus one token of its own. Leviathan et al. (Google, ICML 2023) showed the acceptance rule leaves the output distribution exactly as if the large model had worked alone, and measured 2–3× faster decoding on T5-XXL. The expected yield is (1 − αγ+1) ÷ (1 − α); the speed-up is lower once you pay for the draft model. Gains shrink at large batch sizes, where the spare maths is already in use.

Identity & policy: on whose authority?

Compute and data platforms settled access control years ago with IAM: every call carries a principal, and policy decides what it may touch. AI systems reopen the question, because the caller is increasingly an agent acting for a person. Every layer, from retrieval to tool execution, now has to answer one question: on whose authority is this running, and with what limits?

1 · Authority should narrow at every hop

Governance by design: proving the system does what it should

Governance added at review time produces documents about a system. Governance built in at design time produces evidence of how it behaves. The rule is simple: every intended behaviour becomes a testable requirement, and every requirement leaves a trail that a reviewer or auditor can follow from intent to production.

1 · The traceability chain

  1. Intended useWhat the system is for, who uses it, what it must never do, and its risk tier.
  2. RequirementEach "must" and "must not" written so it can be measured.
  3. Design controlThe mechanism that enforces it: retrieval scope, guardrail, human approval, tool permission.
  4. Eval with a thresholdA test set and pass mark, run in CI. A failed gate blocks the release.
  5. Production monitorThe same check sampled on live traffic, with an alert and an owner.
  6. EvidenceVersioned eval reports, approvals, logs and incidents, produced by the pipeline itself.

Worked example, an HR policy assistant. Intent: answer employee questions from the approved handbook only. Requirement: no answer without a citation to the handbook. Design control: retrieval limited to the handbook index, and the response is rejected if it has no citation. Eval: 300 test questions, at least 95% grounded and zero uncited answers. Monitor: 2% of live answers scored for groundedness each week. Evidence: eval report per release, weekly monitor results, sign-off record.

Layer 2 · a new kind of model

JEV: the model that decides instead of writes

JEV, from TypeSafe AI (early access since 15 September 2026), never writes a sentence. You hand it messy input plus a set of typed questions, and it returns typed answers, each with a calibrated probability. TypeSafe calls it the first System One model, after Kahneman's fast, intuitive System 1. Today's LLMs are System 2 machines: slow, deliberate, and expensive to ask for every small choice an agent makes.

1 · Where it sits: a decision gate in front of the model

Every agent step asks small, bounded questions: which tool, which model, retry or stop, allow or block. JEV answers those in one fast pass. When its confidence falls below a threshold, or the step needs text or free-form arguments, the call escalates to the foundation model. JEV does not replace the LLM; it decides when the LLM is worth calling.

2 · How it works

Typed questions, not promptsYou declare the answer space up front: a yes/no, one of up to 255 labels, a score. JEV can only answer inside it, unlike LLM structured output, which generates first and validates after.
One parallel passNo token-by-token decoding. All questions are answered at once, so many decisions cost roughly one call. TypeSafe quotes 70–500 ms end to end.
Calibrated confidenceTrained with RLCD (Reinforcement Learning for Calibrated Decisions). A 0.9 should be right about 90% of the time, which is what makes a confidence threshold safe to automate on.
Always typed, not always rightJEV cannot hallucinate a paragraph, but it can still pick the wrong label. Evaluate it like any classifier, against your own labelled set.
